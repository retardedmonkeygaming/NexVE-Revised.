# NexVE architecture (baseline)

```
┌─────────────────────────────  https://<host>:8006  ─────────────────────────────┐
│  Browser  ──►  nexved (single Go binary)                                        │
│                 ├── /api/v1/*      REST API  (token / basic auth middleware)    │
│                 ├── /*             embedded web UI (React build, go:embed)      │
│                 ├── node/          CPU/RAM/disk/uptime sampler (gopsutil)       │
│                 └── driver/                                                            │
│                       ├── libvirt.go ──► virsh ──► libvirtd                     │
│                       │                  ├── qemu:///system   (KVM VMs)         │
│                       │                  └── lxc:///          (containers)      │
│                       └── mock.go      in-memory, for UI development            │
└─────────────────────────────────────────────────────────────────────────────────┘
        storage: /var/lib/libvirt/images/*.qcow2      (default libvirt pool)
                 /var/lib/libvirt/images/iso/*.iso    (ISO library)
                 /var/lib/libvirt/filesystems/<name>/ (container rootfs)
```

## Key decisions (and why)

1. **Go, single binary.** The daemon is one statically linked executable that also embeds
   the web UI (`go:embed`). Upgrades = replace one file, restart systemd. Go gives a small
   memory footprint and an easy concurrency model for future work (jobs, websockets).

2. **libvirt via `virsh`, not cgo bindings.** The baseline shells out to `virsh` and parses
   its output/XML with `encoding/xml`. This keeps the binary cgo-free (cross-compilable,
   no libvirt-dev headers), identical on Debian 10–13, and trivially debuggable with
   `virsh` by hand. Swapping in the native bindings later is contained to `libvirt.go` –
   the `driver.Driver` interface does not change.

3. **Domain XML is ours.** VM/container definitions are rendered by NexVE
   (`qemuDomainXML`/`lxcDomainXML`), not by virt-install. That is the foundation for
   owning the guest lifecycle end-to-end (and eventually cloud-init, 9p shares, etc.).

4. **Instance addressing: `<type>:<name>`.** VMs live on `qemu:///system`, containers on
   `lxc:///`; the API ids are `qemu:web-01` and `lxc:dns` so both kinds share one
   endpoint family without id collisions.

5. **Auth now, JWT later.** Bearer token or basic auth, constant-time comparison,
   credentials from `/etc/nexve/nexve.env`. The UI stores the credential in
   `sessionStorage` only. JWT/OIDC is future work (see roadmap).

6. **Dark-first UI.** React + TypeScript + Vite + Tailwind v4, hand-rolled
   shadcn-style components (`frontend/src/components/ui.tsx`), polling (3–5 s) instead of
   websockets for the baseline.

## Request flow examples

Create VM: `POST /api/v1/vms` → `CreateSpec.ApplyDefaults()` (sanitize name, clamp
resources) → `qemu-img create` → optional OVMF lookup → domain XML → `virsh define` →
optional `virsh start` → `201` with the instance.

Create container: `POST /api/v1/vms {type:"lxc"}` → rootfs dir reserved → **202-style
immediate response** with `state:"creating"` → background `debootstrap` → `virsh define`
on `lxc:///` → disappears from `pending` and appears in `virsh list`. Failures stay visible
as `state:"failed"` with the debootstrap tail in `detail`.

## Security notes (baseline level)

- TLS with a self-signed cert (SAN: hostname + primary IP), generated by the installer.
- The web UI is public; every `/api/*` route except `/health` requires auth.
- The daemon runs as the unprivileged `nexve` user (groups: `kvm`, `libvirt`) under
  systemd hardening (`ProtectSystem=full`, `NoNewPrivileges`, `PrivateTmp`, …).
- VNC graphics are bound to `127.0.0.1` only; the console dialog hands out an SSH tunnel
  recipe instead of exposing ports.
- Path containment checks guard `purge` deletes (only files under the managed storage
  directories can be removed).

## Known baseline limitations

- LXC support is experimental (libvirt LXC driver + debootstrap; no templates/CT UI yet).
- No background job system: ISO upload and VM creation are synchronous HTTP requests.
- Console is connection info, not an in-browser terminal (noVNC/websocket = future).
- One node only; no clustering concepts anywhere in the code (deliberately).
